# Contributing

Short guide to contribute:

1. Open an issue

- Describe the problem, steps to reproduce and include logs if possible.

2. Develop locally

- `cd modules/MMM-Webuntis`
- `git submodule update --init --recursive` (only needed if you cloned without `--recurse-submodules`)
- `npm ci`
- `node --run lint` — Biome check
- `node --run test` — unit tests (`node:test`, no external test runner)
- `node --run check` — MagicMirror module checker

Run at least `node --run lint` and `node --run test` before opening a PR.

**Development Container:**
- Recommended: Use the devcontainer for a pre-configured environment
- See [docs/DEVCONTAINER.md](docs/DEVCONTAINER.md) for available tools (httpie, playwright, etc.)
- All dependencies and CLI tools are pre-installed


3. Commit

PRs are squash-merged, so the **PR title** becomes the commit on `develop` and follows
[Conventional Commits](https://www.conventionalcommits.org/). CI checks it with
`scripts/check-commit-msg.js`; the messages of the individual commits in your branch are free-form, because the
squash commit carries the title only (no body). A breaking change is therefore marked with `!` in the title.

```
<type>(<optional scope>): <subject>
```

Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `revert`.

Two things the message actually decides:

- **The changelog.** `CHANGELOG.md` and the version number are generated by release-please from these
  messages. Every type listed above gets a changelog section, so even a `ci` or `chore` commit
  (including Dependabot's) appears in the changelog and opens or updates a release PR.
- **The version bump.** `fix` → patch, `feat` → minor, and a `!` after the type in the PR title → major. Do not edit `version` in `package.json` by hand.

CI also runs `scripts/check-commit-scope.js`, which rejects a `chore`/`docs`/`test`/`build`/`ci`/`style`
PR title when the PR changes runtime source under `lib/`, `plugins/`, `translations/`, `node_helper.js`,
`MMM-Webuntis.js`, or `MMM-Webuntis.css`. Pure formatting and comment-only changes pass. This exists
because a behavior fix once shipped as `chore: update biome schema version` and was missing from the
changelog for months. For a deliberate exception, add `[allow-scope-mismatch]` to the PR title.

The VS Code extension `vivaxy.vscode-conventional-commits` (recommended in `.vscode/extensions.json`,
preinstalled in the devcontainer) gives you a guided form for type, scope, body, and breaking-change
footer.

If you let Copilot draft the message with the ✨ button in the Source Control view, it follows
`.github/commit-instructions.md`, which `.vscode/settings.json` wires up via
`github.copilot.chat.commitMessageGeneration.instructions`. Note that Copilot does *not* read
`.github/copilot-instructions.md` for commit messages — that file only applies to chat and code
generation. Keep the rules in `scripts/check-commit-msg.js`, `scripts/check-commit-scope.js`, and
`.github/commit-instructions.md` in sync when you change them.

4. Create a PR

- Make a branch and open a PR against `develop` with testing steps. CI runs lint, tests, and the PR title checks. The PR is squash-merged, so its title becomes the commit and has to be a Conventional Commit
  as well.

5. Releases

Releases are automated and prepared on `develop`. Every merge to `develop` keeps a
`chore(develop): release x.y.z` PR up to date; it collects changes until you decide to release.
Merging it bumps the version and writes the changelog entry on `develop`, and that is the only manual
step: a PR to `master` (merge commit, not squashed) is then opened for exactly that release commit
and merges itself once its checks pass. The merge tags the release and creates the GitHub release.

6. Style

- Use Biome. Run `node --run lint:fix` to auto-fix style issues.

Thanks for contributing — we review PRs promptly.
